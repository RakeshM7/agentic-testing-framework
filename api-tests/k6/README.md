# API k6 Load Test Scripts — EventHub + Freshsales

Generated by `api-testing-agent`. This directory now covers two independent targets: **EventHub**
(described below) and **Freshsales** (`rakesh-freshsales-ind-sep21` — see "Freshsales target"
section further down).

## EventHub target

From `artifacts/eventhub/api/api-test-plan.md`'s Performance
section. Covers the REST API at `https://api.eventhub.rahulshettyacademy.com/api`.

Scripts cover both the `event-booking` run's original candidates (`events-load-test.js`,
`bookings-load-test.js`, `health-load-test.js`, `booking-creation-load-test.js`) and two candidates
added by the `app-wide` run (2026-09-20): `events-search-load-test.js` (search/filter query
variety) and `auth-login-load-test.js` (login throughput). See
`artifacts/eventhub/api/api-test-plan.md`'s Performance section for the rationale behind each.

## These scripts were generated but NOT executed live during this build

Per the api-testing-agent's hard rule, **`k6 run` was never invoked against
`api.eventhub.rahulshettyacademy.com` or any other live target** while producing this suite. The
`k6` CLI was checked for on this machine (`which k6`) — see the build report for whether it was
present. If it was, only `k6 inspect <script>.js` (static validation of script structure/options,
no network traffic) was run. If it was not, these scripts were manually reviewed instead and that
is noted as an environment prerequisite. This rule has no exceptions: no script in this directory
has ever made a real HTTP request to the live EventHub API during generation.

**If you want to actually run one of these**, that is a deliberate decision for a human to make,
with a target they control:

```bash
k6 run scripts/events-load-test.js
k6 run scripts/bookings-load-test.js
k6 run scripts/health-load-test.js
k6 run scripts/events-search-load-test.js
```

You can override the target host with `-e BASE_URL=https://your-staging-host/api`.

## `booking-creation-load-test.js` needs extra caution

This script performs real `POST /bookings` calls — it creates bookings and decrements real seat
availability on whatever `BASE_URL` it's pointed at. Its default `BASE_URL` is
`http://localhost:3001/api` (the dev server documented in the OpenAPI spec's `servers` list), **not**
the production/demo host, specifically so it can't be run against the shared public target by
accident. Do not override `BASE_URL` to point at `api.eventhub.rahulshettyacademy.com` unless you
own that environment or have explicit authorization to mutate its data — this is the public demo
site used by other testers/students, and creating load-test bookings on it would pollute shared
data (seat counts, booking lists) for everyone else using it.

## `auth-login-load-test.js` also needs caution

This script performs real `POST /auth/login` calls. It doesn't mutate business data (login only
authenticates an existing account), but firing many concurrent login attempts at a shared public
demo account risks looking like credential-stuffing/brute-force traffic to any
rate-limiting/security monitoring in front of the API, and could trigger an account lockout. Its
default `BASE_URL` is also `http://localhost:3001/api`, not the live host, for the same reason.
Point `LOGIN_EMAIL`/`LOGIN_PASSWORD` at a dedicated load-test account you control if you ever run
this, not a real user's credentials.

## Thresholds summary

All read-only scripts assert `http_req_failed rate < 1%` (health: `< 0.1%`) and per-endpoint p95
latency thresholds (see `artifacts/eventhub/api/api-test-plan.md` Performance section for the
rationale behind each number). The booking-creation script additionally expects no HTTP 5xx under
concurrency and documents (via `teardown()` console output) how a human should manually verify no
seats were oversold. The login script similarly documents (via `teardown()`) that a human should
check for 429 (rate-limited) responses before drawing performance conclusions.

## HTML report

`results/report.html` is a static, human-readable summary of every `results/*.json` file, built
deterministically by `node scripts/generate-k6-report.mjs` (run from the repo root; also wired as
`npm --prefix scripts run generate-k6-report`). It reads whatever result JSON files are present,
makes no network calls, and is safe to re-run at any time -- it's the last step api-testing-agent
runs after any `k6 inspect`/`k6 run` validation, and it prints the report's path to stdout.

### Neither script was run live this session (`k6 run` never executed against this tenant)

Both scripts require an authenticated Freshsales session cookie (`FRESHSALES_SESSION_COOKIE` env
var) to do anything meaningful against the live tenant -- and, per the same blocker documented in
`artifacts/rakesh-freshsales-ind-sep21/api/api-test-plan.md`'s "Execution status" section and
`feedback/playwright-automation-agent/2026-09-21-freshsales-recaptcha-blocks-scripted-login.md`, no
authenticated session could be obtained this run (scripted UI login reliably triggers a Google
reCAPTCHA challenge, which this agent does not attempt to bypass).

**What was actually done:** `k6 inspect` (structural/options validation, zero network traffic) was
run against both scripts and both passed cleanly -- valid `scenarios`, `stages`, and `thresholds`,
no syntax/config errors. Neither `k6 run` nor any other network call was made against
`rakesh-freshsales-ind-sep21.myfreshworks.com` by either script.

```bash
k6 inspect scripts/freshsales-contacts-list-load-test.js      # ran this session -- passed
k6 inspect scripts/freshsales-deals-kanban-load-test.js       # ran this session -- passed
```

**To actually run either for real** once a session cookie is available (see the "Freshsales target"
section of `../playwright-api/README.md` for how a human obtains one):

```bash
k6 run scripts/freshsales-contacts-list-load-test.js -e FRESHSALES_SESSION_COOKIE="<cookie>"
k6 run scripts/freshsales-deals-kanban-load-test.js  -e FRESHSALES_SESSION_COOKIE="<cookie>"
```

Both scripts' `teardown()` hooks print a reminder to verify no requests silently 401'd mid-run
(a session expiring partway through would look like *faster*, not failing, latency).

## Safety: explicit `BASE_URL` + host allowlist

No script has a default target. `scripts/lib/guard.js` requires `BASE_URL` and refuses any host not in
`K6_ALLOWED_HOSTS` (comma-separated; localhost/127.0.0.1 always allowed). Static validation therefore needs a
dummy value: `k6 inspect -e BASE_URL=http://localhost:3001 scripts/<file>.js`. Live runs additionally need
`authorizations.mode: full-run` (enforced by `.claude/hooks/guard-bash.mjs` for Claude Code sessions).
