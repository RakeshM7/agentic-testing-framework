# API Playwright Test Suite — EventHub + Freshsales

Generated by `api-testing-agent`. This project now covers two independent targets, each with its
own Playwright project/baseURL in `playwright.config.ts` (mirroring the pattern in
`playwright-tests/playwright.config.ts`): **EventHub** (original target, described below) and
**Freshsales** (`rakesh-freshsales-ind-sep21`, added by the `lead-to-deal-pipeline` run — see
"Freshsales target" section further down).

## EventHub target

Covers the REST API at
`https://api.eventhub.rahulshettyacademy.com/api`, discovered from the live Swagger/OpenAPI spec
(see `artifacts/eventhub/api/discovered-endpoints.json` and
`artifacts/eventhub/api/api-test-plan.md` for the full discovery + scenario matrix).

This suite covers two feature runs against the same underlying 15-endpoint API:
- **event-booking** (original): `auth.spec.ts`, `events.spec.ts`, `bookings.spec.ts`,
  `health.spec.ts`, `config.spec.ts`.
- **app-wide** (added 2026-09-20): `login.spec.ts`, `events-search-filter.spec.ts`,
  `admin-events.spec.ts`, `rbac.spec.ts`. These extend the event-booking files' coverage without
  duplicating it — see each file's header comment for exactly what it adds.

## Guardrail: this suite is read-only (GET) against the live target, plus one sanctioned exception

The target (`api.eventhub.rahulshettyacademy.com`) is a third-party public demo environment, not
something this project owns. Per the api-testing-agent's persona guardrail, this suite defaults to
**GET-only** requests.

**The sanctioned exception is `POST /auth/login`** — used two ways, both non-mutating (they
authenticate existing accounts; they never create, modify, or delete business data):
1. `fixtures/api-fixtures.ts` performs a single `POST /auth/login` call per test worker, using the
   pre-existing, already-verified `EVENTHUB_EMAIL` / `EVENTHUB_PASSWORD` dogfood account
   credentials (loaded from `playwright-tests/.env`), to obtain a bearer token for the
   auth-required and auth-discrepancy test cases (`GET /auth/me`, and the "does GET /events,
   /bookings, or /events (admin) actually enforce a token" checks across the suite).
2. `login.spec.ts` (app-wide) additionally exercises `POST /auth/login`'s negative paths live
   (wrong password, unregistered email, missing fields, malformed email) — each of these is still
   just an authentication attempt against an existing account, the same category of call already
   sanctioned above, just with more payload variety.

The following endpoints are documented in the test plan but **intentionally never called** by any
`.spec.ts` file in this suite, under any payload (valid, invalid, or targeting a nonexistent id),
because they mutate (or would mutate/attempt to mutate) live third-party data:

- `POST /auth/register` (creates a new user) — including invalid-payload attempts; see
  `login.spec.ts`'s header comment for why registration is treated more strictly than login.
- `POST /events`, `PUT /events/:id`, `DELETE /events/:id` (create/modify/delete an event) —
  including the 6-event-max / 7th-event-FIFO-eviction boundary and any attempt to edit/delete the
  "Read-only" seeded events 283/284/285.
- `POST /bookings` (creates a real booking + decrements real seat availability)
- `DELETE /bookings/:id` (cancels a booking) — including the "Clear all bookings" bulk-delete
  frontend feature, which has no dedicated endpoint in the spec anyway (see
  `discovered-endpoints.json`'s `unbackedFrontendFeatures`)

If this suite is ever pointed at a target the user controls (a private/staging environment), those
scenarios are already written out in `artifacts/eventhub/api/api-test-plan.md` and can be
implemented as additional spec files at that point — this generation run does not do so, per the
invocation's explicit scope.

## Setup

```bash
cd api-tests/playwright-api
npm install
npx playwright install --with-deps chromium   # only needed once; API tests don't render pages but Playwright still needs its runtime
```

Credentials are read from `../../playwright-tests/.env` (sibling project at the repo root) via
`playwright.config.ts` — nothing is duplicated here. That file's `EVENTHUB_PASSWORD` value is
intentionally double-quoted because it contains a trailing `#`, which `dotenv` would otherwise
parse as a comment start; if you ever regenerate that file, preserve the quoting.

## Known limitations of this generation

- **Booking-lookup fixtures are conditional.** At discovery time, the dogfood account had zero
  bookings (no `POST /bookings` has ever been made, by this suite or by explore-agent's earlier
  crawl). The "GET an existing booking by id/ref" functional tests in `bookings.spec.ts` look up
  whatever the account actually has at run time and use `test.skip(...)` with an explanatory
  message if there's nothing to look up, rather than fabricating a booking id.
- **Expired-token behavior is not tested.** Minting a pre-expired JWT for the live account would
  require the API's signing secret, which this suite doesn't have. Documented as a gap in
  `auth.spec.ts` and `api-test-plan.md` section 3.
- **The `security` contract discrepancy is tested but not resolved by static analysis alone** — see
  `artifacts/eventhub/api/discovered-endpoints.json`'s `contractDiscrepancyFlag`. The spec declares
  no auth requirement on Events/Bookings routes despite claiming per-account data sandboxing; the
  no-token / valid-token / invalid-token variants in `events.spec.ts` and `bookings.spec.ts` are
  designed to surface whatever the live API actually does, since running them was out of scope for
  this generation pass (see main report).
- **(app-wide) RBAC-bypass testing is documented, not executed.** `rbac.spec.ts` can only confirm
  that no role/permission claim is exposed anywhere in the API (a safe, GET-only schema check).
  Whether `POST`/`PUT`/`DELETE /events` actually reject a non-admin token is a genuinely open
  question that requires calling those routes — out of scope this run regardless of credential. See
  `discovered-endpoints.json`'s `rbacFinding` and `api-test-plan.md` section 19.
- **(app-wide) No non-admin EventHub account exists.** The non-admin-access-to-`/admin/events`
  placeholder case (TC-app-wide-039) is written as a `test.skip(...)` in `rbac.spec.ts` with an
  explanatory message, not silently omitted — same convention as the sibling UI suite's
  `test.fixme()` for the identical case.
- **(app-wide) "Clear all bookings" and the 6-event/FIFO-eviction rule have no endpoint this suite
  calls.** Both are documented-only in `api-test-plan.md` section 18 — see
  `discovered-endpoints.json`'s `unbackedFrontendFeatures` for why (no dedicated endpoint exists in
  the live Swagger spec for either feature).
- **(app-wide) Password-policy contract gap is documented, not executed.** The frontend enforces a
  password complexity policy the backend's documented `AuthInput` schema doesn't require
  (`minLength: 6` only) — see `discovered-endpoints.json`'s `passwordPolicyDiscrepancy`. Resolving
  whether the backend independently enforces it would require a live `POST /auth/register` call,
  which is out of scope this run.

## Freshsales target (`rakesh-freshsales-ind-sep21`)

Covers `https://rakesh-freshsales-ind-sep21.myfreshworks.com`'s internal `/crm/sales/*` app API,
discovered by aggregating explore-agent's per-page `network-requests.json` captures (no OpenAPI
spec exists for this tenant's app API) — see `artifacts/rakesh-freshsales-ind-sep21/api/
discovered-endpoints.json` and `.../api/api-test-plan.md` for the full discovery + scenario matrix.
`mode: full-run` was explicitly authorized for this tenant (the user's own trial account), so these
specs are written to exercise the full GET/POST/PUT/PATCH coverage the test plan calls for — not
GET-only.

### Known blocker: almost none of this suite could run live this session

This tenant's app API authenticates via a **session cookie obtained only through a full interactive
login**, and that login form is gated by a **Google reCAPTCHA challenge that reliably triggers for
scripted browser sessions** — the exact same wall `playwright-automation-agent` already hit and
documented in `feedback/playwright-automation-agent/2026-09-21-freshsales-recaptcha-blocks-scripted-login.md`.
A Playwright `APIRequestContext` cannot solve a visual CAPTCHA any more than a scripted browser can,
and per this agent's hard rule, **no attempt was made to bypass it**.

**What actually ran live this session (real HTTP calls, real pass/fail):**
- `tests/freshsales/auth.spec.ts` — 5/5 passed. Discovered and confirmed a genuine
  **content-negotiated auth-failure contract**: unauthenticated `GET /crm/sales/{contacts,deals,
  sales_accounts}` returns **401** with JSON body `{"login":"failed","message":null}` when the
  client sends `Accept: application/json` (this project's default, and what any real API client
  sends), but **302 → `/crm/sales/signin`** when the client sends `Accept: */*` (curl's default / a
  plain browser navigation). Verified both ways via `curl` first, then reproduced with a real
  Playwright `APIRequestContext` to confirm it wasn't a curl-only artifact.

**Everything else in `tests/freshsales/` is real, runnable code that is currently `test.skip()`-ed**
via `fixtures/freshsales-api-fixtures.ts`'s `skipIfNoSession()` helper, with an explicit reason
printed in the test report — never silently treated as passing, never deleted. To unblock:

1. Have a human complete the Freshsales login once, interactively, in a real browser (solving the
   CAPTCHA themselves).
2. Copy the resulting session cookie value from browser dev tools (Application → Cookies for
   `rakesh-freshsales-ind-sep21.myfreshworks.com`).
3. Set `FRESHSALES_SESSION_COOKIE` in `playwright-tests/.env.freshsales` (see
   `.env.freshsales.example` for the exact key and a caution about quoting values containing `#`).
4. Re-run `npm run test:freshsales` — every skipped test will execute for real against the live
   tenant.

`activities.spec.ts`'s Call-log and Note-creation cases are **additionally** blocked independent of
the cookie: explore-agent never captured a live request for either (only Task creation was
exercised, confirmed `POST /crm/sales/tasks` → 201). Do not guess an endpoint shape by analogy and
assert against it as if confirmed — capture the real request once a session is available, then
replace that file's placeholder `test.skip()` blocks with real assertions.

### created-entities.json

`artifacts/rakesh-freshsales-ind-sep21/api/created-entities.json` is an **empty array** this run —
zero entities were created via the API, since no mutating call could reach past the signin redirect
in the first place. If the suite is re-run after the blocker above is resolved, any test that
actually creates a Contact/Account/Deal/Task must append an entry there (id, resource, endpoint,
created-at) before any subsequent test in the same run targets that entity for a further mutation,
per the full-run destructive-action scoping rule.
