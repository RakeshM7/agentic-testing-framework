# Playwright repo conventions (`playwright-tests/<product>/`)

One repo per product holds both UI and API tests. Every Playwright agent follows this file; reviewers check against it.

## Layout and ownership

```
package.json, package-lock.json, playwright.config.ts, tsconfig.json,
.env.example, .gitignore, README.md, utils/shared/          pw-repo-owner (only), rendered
config/ui/   fixtures/ui/   helpers/ui/   pages/<m>/   tests/ui/<m>/        UI agents (scaffolded by ui-code.mjs, D-055)
config/api/  fixtures/api/  helpers/api/  clients/<m>/ tests/api/<m>/       API agents (generated by api-code.mjs, D-056)
.auth/ (git-ignored storage state)   test-results/{ui,api}/ (git-ignored)
```

### The foundation is rendered from templates (D-054)

The fixed files are not written by hand: `node {fw}/scripts/foundation.mjs render <p> --side repo|ui|api` renders them from the framework's [`templates/playwright/`](../templates/playwright/), which are the source of truth for their code. Each carries a "Generated by scripts/foundation.mjs — do not edit" header (the JSON files are listed in `.foundation-managed.json`), and `foundation.mjs check` and the gate fail on a hand edit.

| Side | Managed (rendered) | Extension (hand-written) | Judgment (cited overlay) |
|---|---|---|---|
| repo | the shared files above (`package.json`'s dependency versions and `package-lock.json` excepted from the drift check) | — | `repo-overlay.json`: dependency names, env names, ignores, whitelisted config values (pw-repo-owner) |
| ui | `config/ui/settings.ts`, `config/ui/README.md`, `fixtures/ui/base.ts` (the mutation guard), `fixtures/ui/auth.setup.ts` | `helpers/ui/` | `ui-overlay.json`: loading indicator, cookie banner, timeouts, a recorded login form (pw-ui-scaffolder) |
| api | `config/api/settings.ts`, `config/api/README.md`, `fixtures/api/base.ts` (the guard, `noAuth`, `malformedAuth`, `identity`), `fixtures/api/auth.setup.ts`, `helpers/api/schema.ts` | `helpers/api/` | `api-overlay.json`: base paths, auth scheme, default headers (pw-api-scaffolder) |

The overlays live in `artifacts/<p>/foundation/`. Dependencies are named without a version: `foundation.mjs install` resolves the latest at creation, and from then on `package-lock.json` pins them.

Within a side: the scaffolder writes the side's overlay and renders the foundation; later it fills only a reported gap, in `helpers/<side>/`. `fixtures/<side>/index.ts` is generated on both sides (D-056): `./base`'s `test` extended with every module's generated registration, in name order, plus `./base`'s `expect` (and `waitForReady` on the UI side). One function (`foundation.mjs` `renderIndex`) renders it for `foundation.mjs render`, `ui-code.mjs build` and `api-code.mjs build`, so all three write the same bytes; it is a managed file no agent writes, and any edit is drift. A previous hand-written index is kept in `artifacts/<p>/foundation/<side>-index.legacy.ts`. The tests-writer fills the module's tests and its data or payload builders in `helpers/<side>/`. The fixer edits any of these except a managed file to apply findings. On the UI side the module's code is scaffolded by a script first, and on the API side it is generated by one (below).

### UI code is scaffolded per approved case and required page template (D-055)

`node {fw}/scripts/ui-code.mjs build|check|paths <p> <m>` (`scripts/lib/ui-code.mjs`) derives what the module needs from the test cases a human approved (D-053) and the exploration's state machine (D-052), and writes the parts that must be identical on every run:

| File (in `playwright-tests/<p>/`) | Owner |
|---|---|
| `tests/ui/<m>/cases.spec.ts`: one `test()` per approved UI case (neither `@api` nor `@performance`), its literal title `TC-<m>-<n> <title> @<priority> @<type> [@mutates] [@assumption] [@visual]`, the page-object fixtures its states need, one `test.step` per case step and one `Then: <expected>` step | the script, **except the marked regions** |
| the regions `// ui-code:begin <key>` … `// ui-code:end <key>` of that file: `setup` (imports, hooks, helpers), one per test for its data (`TC-<m>-<n> data`, at the top of the test) and one per step (`TC-<m>-<n> step <n>`, `TC-<m>-<n> then`) | pw-ui-tests-writer |
| `helpers/ui/<m>.data.ts` | pw-ui-tests-writer |
| `pages/<m>/<slug>.page.ts` per required page template (`PG-` id), `pages/<m>/components/<name>.component.ts` per dialog its states show; `build` seeds a class shell once when one is missing | pw-ui-pom-writer |
| `fixtures/ui/pages/<m>.ts`: the module's page-object fixtures (`type <M>Pages`, `const <m>Pages`) | the script |
| `fixtures/ui/index.ts`: spreads every module's registration on `./base` (generated, D-056) | `foundation.mjs` `renderIndex`, written by the scripts |
| `tests/ui/<m>/_locators.smoke.spec.ts`: the locator smoke (below) | the script |

**Why marked regions.** The generated and the agent-written code share one file: the script owns every line outside the regions, so a rebuild re-renders the skeleton around the file's own region bodies and keeps every body; `check` re-renders it the same way, and any other difference is an edit of generated code. The step bodies close over the test's fixtures, so they need no plumbing. A body whose test is no longer generated (its case was edited and is awaiting a new approval, or a step was dropped) is parked in `artifacts/<p>/modules/<m>/ui-code/parked.json` and restored when its region comes back; a file whose markers are broken is never rewritten.

**Required page objects.** A case touches the states its coverage items name (an input field's states, a transition's two ends, the states its flow file names) and the state snapshots its `observation:` evidence cites. An imported case touches the exploration states testcase-writer's import mode linked it to (D-066); an unlinked imported UI case is not automated. Each page template (`PG-`) of a touched state needs a page object, and each dialog those states show needs a component object. Unapproved cases are never generated, and approved ones over `testcases.max_cases` are deferred (lowest priority first). `ui-code/coverage.json` is the ledger: every case is mapped to its test, excluded (`not-approved`, `api-side`: an `@api` case, or a `@performance` case k6 loads) or deferred (`budget`); every page template is mapped to its page object or excluded (`not-touched`); every dialog is mapped to its component.

**Locator policy.** `getByRole` first, then `getByLabel`, then `getByText`; `getByPlaceholder` and `getByTestId` when the snapshot shows that placeholder or that test-id attribute. Every name is a string literal copied **verbatim and whole** from a stored state snapshot of the page object's own template (`explore/pages/<slug>/states/<ST>.md`; a component: the states that show its dialog):
- a `getByRole` name is a node of that role with exactly that name;
- a `getByLabel` name is a node's whole name;
- a `getByText` (or `filter({ hasText })`, `getByTitle`, `getByAltText`) text is a node's whole name or text;
- a `getByPlaceholder` or `getByTestId` value is an exact recorded placeholder or test-id attribute;
- never a substring.

Options are an object literal: no variable, no spread. These are findings:
- a regular expression, a template literal, a concatenation, a variable or a `String(…)` as a name;
- computed access (`page['getByText']`, `this['row']`);
- a page-object method taken around its call (`.call`, `.apply`, `.bind`);
- a `this.<field>` holding a string passed to `locator(…)`: only a field that holds a locator built by a checked call is a chain.

CSS, XPath, page scripts and Playwright's legacy selector API on a page or frame take a string-literal selector and a cited reason on or up to three lines above: `// locator: css|xpath|evaluate because <reason> [observation:explore/pages/<slug>/states/<ST>.md]`, citing a snapshot of the same template. That covers `locator('…')`, `frameLocator`, `$`, `$$`, `$eval`, `$$eval`, `waitForSelector`, `evaluate*` and `dispatchEvent`, and `page.click`, `fill`, `type`, `press`, `check`, `uncheck`, `selectOption`, `hover`, `tap`, `dblclick`, `focus`, `textContent`, `innerText`, `innerHTML`, `getAttribute`, `inputValue`, `is*`, `setInputFiles` and the like.

**Runtime data (a data-driven locator).** Most `@mutates` cases look up what they created: find the new row, open it, delete their own entity, search for it. A page-object method may build a locator from a `string` parameter `v` only under these conditions:
- it is non-async and only returns the locator;
- that locator is a grounded literal locator refined only by `getByRole('<grounded literal role>', { name: v, exact: true })`, or by `.filter({ hasText: v })` on a grounded container: `row(name: string) { return this.table.getByRole('row', { name, exact: true }); }`.

At each call site `v` is one of:
- a grounded literal;
- in the cases spec, a name from the test's **data region**, directly or through a step-local `const x = <name>.<member>`;
- inside a page object, a string parameter of the calling method, whose own call sites are checked the same way (`async openContact(name: string) { await this.row(name).click(); }`).

Anything else is a finding (`locator-param`). Such locators are left out of the smoke: only their role and container are grounded and checked.

**The per-test data region.** Each generated test opens with `// ui-code:begin TC-<m>-<n> data` … `// ui-code:end TC-<m>-<n> data`, before its steps:

```ts
  test('TC-contacts-1 … @p1 @functional @mutates', async ({ page, contactsPage }) => {
    // ui-code:begin TC-contacts-1 data
    const contact = buildContact();
    // ui-code:end TC-contacts-1 data
    await test.step('1. …', async () => { … await contactsPage.row(contact.name).click(); … });
    await test.step('Then: …', async () => { … await expect(contactsPage.row(contact.name)).toBeVisible(); … });
  });
```

It holds only `const <name> = <builder>(…);` with a builder imported (in `setup`) from `helpers/ui/<m>.data.ts` (rule `data-region`). Its consts are visible to every step of that test and are rebuilt on each retry. A builder called at module level, in `setup` or inside a step binds nothing: its value would be shared between tests and retries, or would never reach the Then step.

Binding is per test: re-declaring, shadowing (a const, a destructuring, a parameter) or reassigning a data name anywhere in the test is a finding (`data-shadow`), and the shadowed value is no longer data. Every builder value a data-driven locator finds is built with `uniqueName` (or `uniqueEmail`) from `utils/shared/data.ts`; a fixed string is a finding (`data-unique`).

**The data builders** (`helpers/ui/<m>.data.ts`) hold data only: values, and functions returning data, built with `uniqueName`. They never import `@playwright/test`, the page objects or the fixtures, never name `Page`, `Locator` or `page`, and never call a locator, selector or page-object method (rule `data-file`). Any other `helpers/ui/` file that the spec or a page object imports is checked under the page-object rules.

**Steps go through the page objects.** A region of the cases spec never finds elements itself (rule `raw-locator`): no `getBy*`, `locator`, `frameLocator`, `$` or `evaluate`, no computed access to them, and no selector-taking `page.<method>(…)` or frame call. `page` appears only for navigation (`page.goto`, `reload`, `waitForURL` …), in `expect(page)` and in `waitForReady(page)`. A page object appears only as `po.<locator>` or `po.method(…)` (rule `po-access`): no computed access, no `.call`, `.apply` or `.bind`, no method taken without being called, never passed on or aliased. A missing locator or action is a request to pw-ui-pom-writer.

A region uses `test` only as `test.step(…)`, plus the hooks (`beforeEach`, `afterEach`, `beforeAll`, `afterAll`) in `setup` (rule `test-reference`, which also catches an alias). testInfo (a hook's second parameter, or `test.info()`) is used only to `.attach(…)` or to read `.title` and `.project`: no assignment, no computed access and no other method (rule `test-info`). A region never calls `.skip(…)`, `.fixme(…)`, `.fail(…)` or `.slow(…)` in any form (rule `silent-skip`).

The only exception parks a case that can't be automated yet: `test.fixme(true, '<reason>');` as the unconditional **first statement** of its first step, never inside any control flow. A parked case is not covered: `coverage.json` lists it under `parked`, its ledger item is excluded with reason `parked`, `check` lists it, and the gate reports it as a minor finding (`approved case parked: <reason>`). Every step of a test that is not parked holds at least one statement.

**The expected-result step really asserts.** It holds at least one top-level `expect(<page object>.<locator or read>).<matcher>(…)`, a web-first or value assertion on a page-object locator or on data read through a page object; for a test with no page object, `expect(page).toHaveURL / toHaveTitle / toHaveScreenshot`. None of these count, and the rule is `no-assertion`:
- `expect(<literal>)`;
- `expect.poll`;
- `expect.soft`;
- an assertion on the page object's own `page`;
- an assertion in a nested block or function;
- an assertion after a top-level `return` or `throw` (code there is a finding of its own).

### The locator smoke (`tests/ui/<m>/_locators.smoke.spec.ts`)

Generated by `ui-code.mjs build` from the plan and the page objects; never edited. One test per required page object, titled `<PG id> <class or dialog> locators resolve @locators-smoke`:
- it opens the page template at a URL one of its explore states recorded, as a path under `BASE_URL` (GET navigation only; query parameters that can carry a credential are dropped); a URL on another host is skipped with the reason;
- a dialog is reached by replaying its state's recorded path from a URL-entered state, and only when every step is safe:
  - a click on a navigation-like control (link, button, tab, menu item, tree item, column header);
  - not inside a form or dialog, and found exactly once in the snapshot of the state it was clicked in;
  - with a name that neither signs out nor commits. The test is the explorer's `mutatesControl` with the control's context, plus the smoke's own words for every role including links: OK, Confirm, Continue, Next, Done, Submit, Apply, Save, Add, Empty, Clear, Remove, Archive, Send, Delete, Buy, Cart, Pay, Star, Favorite, Follow, Subscribe, Like, Pin, Mute, Block, Report, Accept, Decline, Watch, Unwatch, Bookmark, Retry, and Open, unless the control is a link to a page;
  - followed by a recorded transition into a state for which the exploration's network inventory holds no request other than GET.

  Each click targets the recorded element exactly (`getByRole(role, { name, exact: true })`), asserts `toHaveCount(1)`, then clicks; there is no `.first()`. A path that fails any condition makes the test a `test.skip(true, '<reason>')`;
- it asserts `await expect(<fixture>.<locator>).not.toHaveCount(0)` for each public locator property of the page object whose `getBy*` names the visited state's snapshot shows; locators only another state shows are listed in a comment. A data-driven locator (runtime data, above) is left out: its value exists only at run time, and its role and container are grounded by the check.

It is readonly-safe **in every mode**: no typing, no commit click, no `@mutates`, and its own `beforeEach` routes every request: a GET goes on (to the mutation guard, which is off in a full-run), anything else is aborted and recorded, and the `afterEach` fails the test when one was attempted. The UI runner-triager runs it **first** (`--grep @locators-smoke`), then the cases (`--grep-invert @locators-smoke`). Its failures are classified by `triage.mjs` like any other test (§7 of the hand-off formats, D-058):
- a page-object locator that does not resolve on a page that loaded (a count of 0): `locator-drift`, by rule, healable. The fixer re-grounds the locator verbatim in a snapshot, then runs `ui-code.mjs build` (the smoke follows the page objects);
- a recorded click whose control is gone: an open row; the triager classes it `test-bug`, not healable. The exploration is stale, and the module needs re-exploring;
- the page did not load (an error status, a login page, the host down): `environment` (by rule when the error names an unreachable target or a missing session, else the triager's call);
- a skipped smoke test is a skip with its reason, not a failure.

The gate traces the smoke's tests to page templates, not to cases, only at the exact path `tests/ui/<m>/_locators.smoke.spec.ts` of a scaffolded module (one with `ui-code/plan.json`): each of its tests must carry `@locators-smoke`, and the file must stay byte-identical to its render; `check` and the gate flag any edit. In compile mode the gate also flags an alias of `test`, a case id Playwright lists twice or that is not an automated case (on the API side too once `api-code.mjs` generated the module: one test per plan scenario, D-056), and any difference between the tests listed in `cases.spec.ts` and the plan's (one each).

### API code is generated from the catalogue and the plan (D-056)

`node {fw}/scripts/api-code.mjs build|check|paths <p> <m>` (`scripts/lib/api-code.mjs`) generates the module's API code from the endpoint catalogue (D-045, built by the `api-discovery` stage, D-067) and the verified API plan (D-046, D-050; every scenario linked to a signed-off `@api` case is p1). Only scenarios the plan holds are automated, and the plan links only test cases a human approved (D-053).

| File (in `playwright-tests/<p>/`) | Owner |
|---|---|
| `clients/<m>/<resource>.client.ts`: one class per resource, one method per catalogue endpoint (`list`, `read`, `create`, `update`, `delete`, else the `operationId`; a clash adds the HTTP method), taking `{ path, query, headers, body }` and returning the raw `APIResponse`. GraphQL: one method per operation, a query sent as GET when the server accepts it. `send(method, path, …)` serves the plan's unsupported-method scenarios only | the script (managed) |
| `clients/<m>/types.ts`: request, response, query and variables types from `requestSchema` and `responseSchema` (a small built-in JSON Schema to TypeScript generator; key names seen only in traffic are marked unverified) | the script (managed) |
| `clients/<m>/support.ts`: types and pure helpers only (JSON pointers, the plan's mutations, `unknownId`, `bodyOf`, `refOf`, the assertions' helpers); no session, ledger or sender function | the script (managed) |
| `clients/<m>/sender.ts`: the one request sender, through the guarded context a fixture hands out, and the test session (`beginTest`, `createdBy`, `invalidPath`, `planned`, `mergeAgent`). Imported only by the generated clients and specs | the script (managed) |
| `config/api/schemas/<m>/<resource>.json`: the JSON schemas per operation, with a `$comment` "do not edit" header (OpenAPI `nullable` becomes a JSON Schema null type) | the script (managed) |
| `fixtures/api/clients/<m>.ts`: the module's client fixtures (`type <M>Clients`, `const <m>Clients`), each built on the guarded `api` | the script (managed) |
| `tests/api/<m>/<resource>.spec.ts`: one literal `test()` per plan scenario (below) | the script (managed) |
| `helpers/api/<m>.payloads.ts` and `helpers/api/<m>.glue.ts`: everything outside their slots | the script |
| the slots `// api-code:begin <key>` … `// api-code:end <key>` of those two files, and `artifacts/<p>/modules/<m>/api-code/tests-overlay.json` (`park`, `glue`) | pw-api-tests-writer |
| `clients/<m>/facade.ts`: per client `<Class>Facade`, the reads and plain creates only (frozen bound functions), for glue and composite helpers | the script (managed) |
| `fixtures/api/index.ts`: spreads every module's registration on `./base` | `foundation.mjs` `renderIndex`, written by the scripts (managed) |
| `artifacts/<p>/modules/<m>/api-code/client-overlay.json` (cited naming fixes and edge cases), `helpers/api/<m>.composite.ts` (seeded once) | pw-api-client-writer |

A managed file carries "Generated by scripts/api-code.mjs — do not edit". `check` compares every one with a fresh build, and during a run the guard denies every caller a direct write (`config/permissions.yaml` `managed_files`). A file in a generated folder that no build made is a finding.

**The tests.** Each test's literal title is `API-<m>-<n> <the plan's title> @<priority> @<type> [@mutates] [@identity-<name>…] [@TC-<m>-<n>…]`. The `TC-` tags name the test cases a human approved now; an edited case loses its tag until it is approved again. The body is generated from the scenario:
- **Setup.** Each path parameter comes from its producer at its pointer: a list the run reads, or a create the run records. A failed setup is a precondition that throws; it is not an assertion.
- **The request** goes through the generated client:
  - the payload builder's valid (or `changed`) body, then the plan's `values`;
  - then exactly the plan's one `mutation`: a body pointer, a query, header, cookie or path parameter, or a GraphQL argument. `each` loops over its values. An `unknown-id` (or `target: unknown-id`) on a read is a valid id that does not exist; on a request that changes data it is an entity the test created and deleted first, and without a create with a delete operation on that path the scenario is a `test.fixme` with the reason (U3: never a made-up id for a change);
  - `headers`, `repeat`, `select` and the `dependency` parts; an unsupported `method` goes through `send`.
- **The auth context.** The default is the resource's client fixture, the run's session. `none` builds the client on `noAuth`, `malformed:<scheme>` on `malformedAuth(<scheme>)`, and `identity:<name>` on `identity(<name>)`.
- **The assertions, in the plan's order.** Every message names the expectation's source, and no agent ever writes a status or schema assertion.
  - The status: `toBe(<status>)` when a source gives it, `[…].includes(status)` for `statusIn`, the class bounds for `2xx` and `4xx`, `< 500` for `non-5xx`. Never a 5xx.
  - The schema: `validateSchema` against the response schema, or the error schema under its status.
  - Each rule under its `when`: `keys-present`, `present`, `absent`, `equals`, `not-equals`, `contains`, `errors-present`, `errors-absent`, `header-present`, `ignored-if-accepted`, `reflects-update`.
- **Lifecycle** scenarios run their `steps` in order, each bound to an earlier response's pointer and asserted with its own expectation.
- **The ledger and cleanup.** A response that may have created something (a create, a setup producer, a step, the glue) is recorded at once with `recordCreated`. In `finally`, each entity is deleted through its delete operation only when `owns()` says this run created it, then `recordDeleted`. Without a delete operation it stays, recorded (`leavesData`).
- **A blocked scenario** (the plan's `blocked`, or a request the plan gives no value for) and a **parked** one are `test.fixme(true, '<blocked|parked>: <reason>')` as their only statement.

**The payload slots.** `helpers/api/<m>.payloads.ts` holds one builder per valid request body, changed body, required query or header parameters, GraphQL variables or dependency parts that a runnable test needs. Each returns the generated request type. Its slots hold data only: plain values and pure functions, with unique values through `uniqueName` or `uniqueEmail`. No request, client, fixture, `test`, `expect`, environment, global, `await`, `throw` or type escape.

**The glue slots.** `helpers/api/<m>.glue.ts` holds one `arrange…(c, given)` per business scenario (rule `overlay`) that the tests overlay asks glue for, with a citation. It runs after the generated setup, reads the setup's values as `given.path.<parameter>`, and returns `{ path?, body? }`, which the request uses (`arranged.path?.<p> ?? <setup value>`; the body is the builder's, then the plan's values, marked planned, then `mergeAgent(body, arranged.body)`, which refuses a field that would replace a value the plan sets). It may use `c` only as:
- `c.clients.<client>.<method>(…)`, a method of the facade: reads and plain creates (a POST to a collection that is not action-like or destructive by its path, `operationId` or summary), never `send()`, a delete, an update or an action;
- a client argument of `composite.<helper>(…)`;
- `c.track(res)`, which returns the entity a create of this test made, and throws for any other response.

Both slot files also have an `imports` slot that holds only `import { … } from './<topic>';` of the scaffolder's `helpers/api/<topic>.ts`, which is then checked as agent code.

**The run-time checks** (the managed sender, `clients/<m>/sender.ts`). Every test opens a session (`beginTest` with `recordCreated`, `recordDeleted` and `owns`) and ends it in `finally`. The sender records every create in the ledger at once, as (entity type, canonical id), accepts `c.track` only for a create it marked, and records a delete of an owned id. Before anything is sent it refuses:
- a path value without its schema's format (an integer `/^(0|[1-9]\d*)$/`, a number, a uuid, else one plain segment), reads included; only the generated spec's `invalidPath(…)` sends the plan's wrong-type value;
- a request other than GET, HEAD or OPTIONS whose path value is not an entity of the parameter's type this test created (its created-and-deleted `goneId` included); a reference of no known type names nothing it owns;
- a request other than GET, HEAD or OPTIONS, or a GraphQL mutation, whose body, query or variables carry an `id`, `ids`, `<x>Id`, `<x>Ids` or `<x>_id` field (any depth, arrays too) that is not an owned id of its referenced type, unless the generated spec marked it `planned(…)` (the plan's own values);
- the same for a field whose schema has an id format (uuid, or a string format a path parameter of the catalogue has), for any value, and for a field named after a resource or path parameter of the catalogue (singular or plural: `contact`, `contacts`, `owner` when an `owners` resource exists; generic words excepted), for an integer or uuid value;
- on a destructive or action endpoint (or a create whose summary or `operationId` sounds like one), every integer or uuid in an array of the body, and every uuid anywhere in it, that is not an owned entity of the endpoint's type.

Known limit: a reference in a field with none of these names or formats (`target: 99`, `ref: 99` without a format) is not seen, because plain integers can't be told from references and the catalogue's `$ref`s are dereferenced. The reviewer checks payload builders and glue for such fields.

 `session.end` deletes, in reverse, only what the ledger says this run owns and is still there; a type without a delete operation stays recorded. The assertions' helpers use built-ins captured when the sender loads. Glue and composite helpers get only the facade.

A rebuild keeps every slot body. A body whose slot is no longer generated is parked in `api-code/parked.json` and restored when the slot returns; a file with broken markers is never rewritten.

**Composite helpers** (`helpers/api/<m>.composite.ts`) take facade clients as parameters (`<Class>Facade`) and call their methods only. No `send()`, no delete or update, no assertion, no raw request.

**What agent code may use** (the composite helpers, the slots, the scaffolder's gap files):
- values imported only from a gap file, any module's `support.ts`, `types.ts` or `facade.ts`, a module's payload builders and `utils/shared/data.ts`, and only names the file exports; types from anywhere with `import type`. Never the sender, a client class, the fixtures, a package, a re-export, a side-effect import or a run-time load. The check follows imports from the specs and slot files through every gap file;
- identifiers from an allowlist (`scripts/lib/agent-scope.mjs`): what the code declares or imports, the generated bindings (`c`, `given`, `payloads`, `composite`), and the pure globals `PURE_GLOBALS` lists (`String`, `Number`, `Boolean`, `Math`, `JSON`, `Date`, `Array`, `Object`, `Map`, `Set`, `URLSearchParams`, `Error`, `Promise`, `encodeURIComponent` and the like), each only called, constructed, with a listed member called (`Object.keys(x)`) or a listed constant read. A global is never a value: no alias, argument, spread or destructuring. No name shadows a global;
- member assignment only on an object the same code created (an object or array literal, or `new …`), never on a parameter or an alias;
- no property named `constructor`, `prototype`, `__proto__`, `caller`, `callee` or `arguments`, in any position: a member, an object or destructuring key (nested or renamed), a string or a template's text (so not in an `in` check or a descriptor lookup either) (rule `forbidden-property`);
- no computed member access or computed key (`o[k]`, `o?.[k]`, `{ [k]: v }`, `const { [k]: v } = o`) but a number literal or a `for (let i = <number>; …)` counter that is only stepped (rule `computed-access`). These two rules read the JavaScript that runs, so types (`T['name']`) are not affected.

**The client overlay.** Naming fixes (`classes`, `methods`) and edge cases (`content-type`, a fixed non-credential `header`, a `note`) are cited.
- A `spec:` citation names the endpoint's own node of its spec source, or a node inside it: never the whole file or another operation.
- A name must be spelled by whole words of a cited source, and a value must appear there as a whole token.
- A credential header, a URL or a key-like value is refused.

**Check rules.** `node {fw}/scripts/api-code.mjs check <p> <m> [--clients]` runs them, and so does the gate:
- `generated`: a managed file missing, edited or out of date; `extra-file`: a file no build made in a generated folder;
- `missing-test`, `extra-test`, `duplicate-test`, `title-drift` (the title or tags);
- `fixme`: a blocked or parked scenario not `test.fixme` with its reason; `silent-skip`: a runnable test skipped, failed or fixme;
- `no-assertion`; `assertion`: `expect(<literal>)`, `expect.soft`, `expect.poll`;
- `ledger`: a test that opens no session with `recordCreated`, `recordDeleted` and `owns`, or never ends it;
- `raw-request`: `request`, `newContext`, `fetch`, axios, node `http`, the raw sender, a constructed client;
- `client-assertion`;
- `fixture-registration`: `fixtures/api/index.ts` not its render;
- `builtin-patch`: an assignment to or delete of a member of a built-in, a prototype, globalThis or an object the code did not create (a literal or a construction), `Object.assign` onto anything but a new literal, `defineProperty`, `getPrototypeOf` and the like;
- `free-identifier`: an identifier outside the allowlist, a pure global used as a value, a shadowed global, or code that does not strip to JavaScript;
- `session-reach`: agent code importing the sender, a client class, the fixtures, or a name its target does not export; `re-export`: an agent file re-exporting;
- `test-runner-import`: a helper, page object or composite helper importing `test` or `expect` (both sides, also in the gate);
- `imports`: an `imports` slot holding anything but an import of a gap file;
- `skeleton`: a slot file edited outside its slots, or broken markers;
- `payload-slot`, `glue-slot`: an empty slot a scenario needs;
- `data-only`, `type-escape`, `glue`, `composite`, `shadow`, `test-reference`;
- `forbidden`: a global, the environment, the runtime; `computed-access` and `call-apply-bind`;
- `hardcoded`: a URL, the target's host or a credential, however the string is escaped or joined;
- `typecheck`: `tsc`.

Any `helpers/api/` file that the module's files import is checked as agent code too. An older module with hand-written files in a generated folder or other `helpers/api/<m>.*.ts` files: `api-code.mjs build --adopt` moves them to `api-code/legacy/`. A plain build keeps a hand-written file with a generated name there too, with a warning, before it writes the generated one.

A change to a file you don't own, or to a managed file, is a request in your report to your orchestrator — never an edit. The guard denies every agent a direct write to a managed file.

## Projects (`playwright.config.ts`)

`setup-ui` (testMatch `fixtures/ui/*.setup.ts`) → `ui` (testDir `tests/ui`, depends on `setup-ui`, storage state `.auth/ui.json`), `setup-api` (`fixtures/api/*.setup.ts`) → `api` (testDir `tests/api`). TypeScript, `fullyParallel: false` by default, retries `2`, trace `on-first-retry` (D-058: a failed test is retried twice, and passing on a retry is `flaky` by rule), reporters `list`, `json` (`test-results/report.json`) and `junit` (`test-results/junit.xml`) for runs outside the framework (the runner passes its own `--reporter`), a rendered CI workflow `.github/workflows/playwright.yml` that runs the suite readonly once the folder is its own repository (D-080), output in `test-results/<side>/`. The only setup file of a side is the rendered `auth.setup.ts`; Playwright lists its setup test with the side, and the gate does not count it as a test.

## Environment (`utils/shared/env.ts`; values from `.env`, never hard-coded)

`BASE_URL`, `API_BASE_URL`, `STORAGE_STATE` (path to a human-produced storage state, optional), `ATF_MODE` (`readonly` | `full-run`, set by the runner from `state/run.json`), `ATF_PRODUCT`, `ATF_RUN_ID`, `ATF_REPO_ROOT` (framework repo root, for the ledger); `LOGIN_USERNAME` / `LOGIN_PASSWORD` (UI credential login) and `API_TOKEN`, `API_KEY`, `API_USERNAME`, `API_PASSWORD` (the API auth scheme's variable). Credentials only via the `.env` file the run-config's `credentials_file` points to. `.env.example` lists names with empty values.

## Login (`fixtures/<side>/auth.setup.ts`)

`STORAGE_STATE` always comes first. A UI credential login is rendered only when the UI overlay cites a plain login form the exploration recorded as a state; its selectors are that snapshot's own roles and names. CAPTCHA, MFA or a login on another host (single sign-on) is never automated: setup fails with an instruction to provide `STORAGE_STATE`. The API's `session` scheme reuses `STORAGE_STATE` or the UI's `.auth/ui.json`; header schemes read their variable per request.

## Safety in code

- A test that creates, changes or deletes data has `@mutates` in its title. The config sets `grepInvert: /@mutates/` unless `ATF_MODE === 'full-run'`.
- UI fixtures install a mutation guard (`fixtures/ui/base.ts`, an auto fixture): when `ATF_MODE !== 'full-run'`, requests to the product's hosts with a method other than GET/HEAD/OPTIONS are aborted. The product's hosts are the run-config's `target.url` and `target.api_urls` hosts, rendered into `config/ui/settings.ts` as `productHosts` (D-073), plus those of `BASE_URL` and `API_BASE_URL`, each with its subdomains. In a full-run the same guard aborts a destructive request to them (any DELETE, or a non-safe method whose path names a destructive action) unless a path segment or query value is a live entity of this run, and fails the test with `Delete blocked by the ledger guard (D-005)` (D-074). API fixtures (`fixtures/api/base.ts`) wrap every request context in `guarded()`, so non-GET calls throw `Mutation blocked: readonly run` outside full-run. `fixtures/<side>/index.ts` always builds on `./base`. Auth setup files are the only exemption (they must log in).
- Every entity a test creates is recorded immediately with `recordCreated({ type, ref, module, label })` from `utils/shared/ledger.ts` (it runs `node $ATF_REPO_ROOT/scripts/ledger.mjs add …`), deleted only after `owns(type, ref)` is true, and recorded with `recordDeleted`. Clean up in `afterEach`/`afterAll`. `ref` is the id the product uses for the entity (the one in its URLs, read from the page or the response), never a display name: the UI guard matches it against the URL of the delete. The API sender also records each create's cleanup recipe (`cleanup: {endpoint, param}`), which `ledger.mjs sweep` uses later (D-075).
- Test data is unique per run: `uniqueName(prefix)` from `utils/shared/data.ts` (includes `ATF_RUN_ID`).

## Code rules

- Test titles start with the test case id: `test('TC-contacts-3 creates a contact with required fields @mutates', …)`. One `describe` per test case group; tags in titles mirror the test case tags (`@p1`, `@negative`, …). On the UI side `ui-code.mjs build` writes the titles, tags and steps (D-055).
- Locators: `getByRole` / `getByLabel` / `getByPlaceholder` / `getByTestId` first; text copied verbatim from `explore/pages/<slug>/dom-snapshot.md`; CSS/XPath only when nothing else exists, with a comment why. On the UI side the stricter locator policy above applies, checked against the state snapshots.
- No `waitForTimeout`, no fixed sleeps; web-first assertions (`await expect(locator).toBeVisible()`).
- Page objects (`pages/<m>/<page>.page.ts`): class per page, constructor `(page: Page)`, locators as readonly properties, actions as async methods, **no assertions**.
- API clients (`clients/<m>/<resource>.client.ts`): generated by `api-code.mjs`, a class per resource wrapping the guarded context, typed request/response, **no assertions** (D-056).
- Helpers (`helpers/<side>/`): pure functions (builders, formatters, parsers); no Playwright fixtures inside.
- Fixtures (`fixtures/<side>/index.ts`): generated (D-056), `./base`'s `test` extended with every module's generated registration (`fixtures/ui/pages/<m>.ts`, `fixtures/api/clients/<m>.ts`), and `./base`'s `expect`. The guard (the UI mutation guard, the API's guarded contexts) lives in the rendered `fixtures/<side>/base.ts` and the login in `auth.setup.ts`. No helper or page object imports `test` or `expect`.
- Visual checks (`@visual` cases): `toHaveScreenshot()` with masks for dynamic regions; baselines are created by the runner with `--update-snapshots` only when none exist.
- `npx tsc --noEmit` must pass before handing back.

**Machine-checked** by `scripts/gate.mjs` before every review (findings in `gate-findings.md`): typecheck and `--list`; one test (or `test.fixme`) per test case (ui, all but `@api`) or plan scenario (api), and no test without one; `@mutates` in the title of every test whose case or scenario mutates; `recordCreated` in UI specs with `@mutates` tests; no `waitForTimeout`; no hard-coded URLs or `test.only`; no assertions in page objects or clients; once the foundation is rendered, no managed file drifted from its render, `fixtures/<side>/index.ts` builds on `./base`, and no setup file but `auth.setup.ts`. Once a UI module is scaffolded (D-055), the gate also runs `scripts/lib/ui-code.mjs`'s rules: the cases spec's skeleton intact (no missing or extra test, no changed title or tags), no empty step body, an assertion in each expected-result step, `toHaveScreenshot` in every `@visual` test, `recordCreated` in every `@mutates` test's own steps, the required page objects present and registered, every locator grounded, no selector without a cited reason, and the registration and smoke as generated; `node {fw}/scripts/ui-code.mjs check` runs the same rules (with `--pages`, the page-object ones and `tsc`). On the API side the gate runs `scripts/lib/api-code.mjs`'s rules (above) instead of title rules of its own, and an API module whose code was never generated is a blocker (D-056). `node {fw}/scripts/foundation.mjs check` enforces the rest of the foundation's rules. Its URL check flags a full URL, a protocol-relative `'//host'`, and a URL assembled from pieces (a scheme joined with `+`, through `${'…'}`, or an array holding a scheme piece that is joined); a bare host literal such as `'acme.example.com'` is out of its scope and left to the reviewer. Everything else in this file is the reviewer's to judge.

## Running (runner-triagers only)

```
ATF_MODE=<run mode> ATF_PRODUCT=<p> ATF_RUN_ID=<run> ATF_REPO_ROOT=<repo> \
PLAYWRIGHT_JSON_OUTPUT_NAME=test-results/<side>/<m>-report.json \
npx playwright test --project=<side> tests/<side>/<m> --reporter=list,json --output=test-results/<side>/<m>
node $ATF_REPO_ROOT/scripts/results.mjs playwright <p> <m> <side> playwright-tests/<p>/test-results/<side>/<m>-report.json
```

The UI runner makes one run of `tests/ui/<m>`: the module's locator smoke (`_locators.smoke.spec.ts`, whose file name sorts first) and the cases land in one report, because `results.mjs` takes one report; the smoke's items carry `smoke: true`. See "The locator smoke" above for how its failures are classified (D-055, D-058). `node {fw}/scripts/triage.mjs prepare <p> <m> --domain <side>` clears `test-results/<side>/` before the run; `triage.mjs build` and `check` follow `results.mjs` (`docs/agent-handoffs.md` §7). Retries come from the config, never from the command line.
