# k6 conventions (`k6-tests/<product>/`)

## Layout and ownership

```
lib/                 k6-lib-writer      config.js, auth.js, checks.js, data.js, summary.js, settings.js (rendered)
lib/ext/             k6-lib-writer      hand-written additions for missing exports
scripts/<m>-*.js     scripts/k6-code.mjs  one generated script per workload scenario (K6-<m>-<n>), never edited
scripts/slots/<m>.js k6-script-writer   the slots of the module's scripts: data, path, query, body, checks
results/             k6-runner-triager  <script>.summary.json, <script>.created.json, <script>.retry.summary.json, <script>.retry.created.json and <script>.retry.untracked.json (the smoke re-run; its leftovers go to the ledger too) (git-ignored)
README.md            k6-lib-writer      how to run, env vars (rendered)
```

The lib, the README and `.gitignore` are rendered by `node scripts/foundation.mjs render <p> --side k6` from the framework's [`templates/k6/`](../templates/k6/), which are the source of truth for their code (D-054). Each carries a "Generated by scripts/foundation.mjs — do not edit" header; the guard denies a direct write, and `foundation.mjs check` and the gate fail on a hand edit. k6-lib-writer's judgment (the auth scheme, base path, default headers, missing-export requests) lives in its cited overlay `artifacts/<p>/foundation/k6-overlay.json`, and its own code in `lib/ext/`. `foundation.mjs check --side k6` runs `k6 inspect` on a temporary script of its own that imports every lib file.

## The workload is script-built from the approved @performance cases (D-068)

`node scripts/workload.mjs build|check|paths <p> <m> [--run <run-id>]` writes `artifacts/<p>/modules/<m>/k6/workload.json`, `workload-coverage.json` and `workload-registry.json` from the module's human-approved `@performance` test cases (the only source of load), the endpoint catalogue of the `api-discovery` stage, the run-config's `k6` section and the designer's cited `workload-overlay.json` (priorities, mixes and weights, think time, data needs, exclusions, write flows). `--run` names the active run or a run of the product with a results folder. The k6-workload-designer writes only that overlay. k6 does not need the Playwright API tests.

- **One load unit per case.** A `@performance` case names an `endpoint` (an `EP-` id) or a `flow` (an overlay flow or mix of that name), a load type, a target rate and optionally an SLO. Its scenario is keyed `case:<TC id>|<type>`. A case whose endpoint the catalogue lacks is excluded as `unknown-endpoint`, one whose flow no overlay entry resolves as `unresolved-flow`; both are also noted.
- **Test types by mode.** A readonly run gets smoke only; a full-run gets smoke and average-load. Stress, spike, soak and breakpoint run only when the run-config opts the module in: `k6.modules.<m>.types: [stress, spike, soak, breakpoint]`. A case's type is capped the same way: smoke in readonly, average-load for an opt-in type that is not opted in, each cap noted (`requestedType` in the ledger).
- **Known functional failures are skipped.** When the module has Playwright API results (this run's, else the latest earlier run's), mapped to endpoints through the API plan's scenario ids, a case whose endpoint a failed (or flaky) scenario touches is excluded as `failed-functional`, and one whose endpoint's functional scenarios are all blocked and none passed as `blocked`; a flow or mix case only when one of its endpoints failed. Without results every case is load-tested, with a note.
- **The open model.** Every scenario is an arrival-rate executor (`constant-arrival-rate`, or `ramping-arrival-rate` starting at 0 for stress, spike and breakpoint): the rate is what the product gets, whatever its latency.
- **Little's-law sizing.** `preAllocatedVUs = max(1, ceil(peak rps × expected iteration s × 1.5))` and `maxVUs = 2 × preAllocatedVUs`. The expected iteration time is the requests' p95 (the SLO, else the assumed 1000 ms) plus the cited think time; a flow sums its steps, a mix takes its slowest member.
- **Dropped iterations.** Every scenario has `dropped_iterations: count<max(1, ceil(1% of the planned iterations))`, so a load generator that can't deliver the rate fails the run instead of passing quietly.
- **Caps.** A case's rate is its target rps, never above the caps. The read cap is `k6.slo.rps`, else `k6.caps.rps` (default 10 rps); a write gets half of it unless an SLO says otherwise; nothing goes above 50% of a documented rate limit, and a type with no headroom left is skipped as `rate-limited`. The write cap holds at every peak: a write scenario's (a flow's, or a query-like POST's) stress, spike and breakpoint ramps are scaled down, their base rate becoming the write cap divided by the profile's peak factor, so the peak is at most the write cap (`load.writeCapRps`). A query-like POST runs at the write cap in every type, average-load included, so its stress peak is never below its average (confirmed by the user on 2026-10-19). A ramp under one request per minute is skipped as `rate-limited`. Average-load lasts `k6.caps.duration_s` (120 s), soak `k6.caps.soak_duration_s` (1800 s), smoke 30 s at 1 rps.
- **Thresholds, SLO or assumed.** `http_req_duration` (p95, p99 when given) and `http_req_failed` per endpoint come from the case's `load.slo`, else `k6.slo` (per endpoint, module or product), field by field. Without one they are conservative defaults (p95 < 1000 ms, error rate < 1%) marked `assumed` in `workload.json`; surfaced in the report by G11. Threshold metrics are tagged by endpoint (`http_req_duration{endpoint:EP-…}`).
- **Writes only in full-run, through flows, on entities the flow created (D-005).** A mutating endpoint loads only in a full-run, and only through a cited overlay flow. `flowProblems` enforces the rules in `workload.mjs build` and `check`, and again in `k6-code.mjs build` and `check`:
  - step 0 is a top-level create (no path parameter);
  - every path parameter of every later step is bound (`bind` is one `{param, from, pointer}` or an array of them), and every bind comes `from` a create step of the flow with that create's **id pointer**: the documented create response id (a catalogue link from the create, the delete's first), else `/id`. A bind from a read step or to any other field (`/ownerId`, `/accountId`) is refused;
  - a bound parameter names an item of the collection its create created in, and a read, update or delete is on its entity's resource. A nested child path binds the parent to step 0 and the child to a **child create** of the same flow (a create with path parameters);
  - a **cleanup delete** deletes the created entity itself: a DELETE whose path is the create's collection path plus exactly one `{param}`, bound to that create's id. Only such a delete is the flow's cleanup and only it is followed by `trackDeleted`. A DELETE on any sub-path (`/contacts/{id}/assign`) is an ordinary write step under the bind rules, never a cleanup; a created entity with no cleanup delete stays tracked as a leftover for the ledger;
  - the cleanup deletes are the last steps, each created entity at most once, children before their parent.

  Each iteration creates its own synthetic entities and records every one with `trackLeftover` at once; a write never gets a `path:` slot. A mutating endpoint no loaded flow covers is excluded as `no-safe-data`. A query-like POST (a search that creates nothing) loads only in a full-run, without a flow, at the write cap in every type, still `mutates` for the guard. A query-like endpoint on an item path (any `{param}`, such as `/contacts/{id}/archive`) loads only as a flow step bound to a create, as a write step under the bind rules; standalone it is excluded as `no-safe-data` ("query-like on an item path"). A query-like request never gets a `path:` slot.
- **The ledger.** Every approved `@performance` case is loaded, excluded with a reason (`unknown-endpoint`, `unresolved-flow`, `overlay-excluded`, `mutating-readonly`, `failed-functional`, `blocked`, `rate-limited`, `no-safe-data`), or `deferred: budget` (`k6.budget` counts cases per module, ranked by the case's priority, then the overlay's, then the TC number). `not-planned` and `untested-functional` are retired (D-068).

## Scripts are generated (D-057)

`node scripts/k6-code.mjs build|check|paths <p> <m>` (variant A of the script-built agents) writes one managed script per `workload.json` scenario, `scripts/<m>-<name>.js`, headed "Generated by scripts/k6-code.mjs — do not edit" with its `K6-<m>-<n>` id, plus `artifacts/<p>/modules/<m>/k6/code-plan.json`. A script holds:
- `options` copied verbatim from the scenario's `options` in `workload.json`;
- `setup()`: `assertAllowedHost()`, `requireFullRun(<mutates>)`, then the data slot;
- every request as `http.request(<method>, url(<path>), <body>, params({ tags: { endpoint: '<EP id>' } }))`, then `checkStatus` against the API plan's expected status (exact, a list, or any 2xx when the plan gives only the class) and the checks slot. The path is relative to the k6 overlay's `basePath`, which `url()` prepends (catalogue paths include the server's base path);
- a mix's weighted pick; a flow's chain:
  - every create (step 0 and each child create) **returns unless its status is the plan's expected create status** (any 2xx when the plan has none), so a 409 or an error body never names what later steps touch;
  - then it reads the id at the create's id pointer and calls `trackLeftover(<resource>, <id>)` at once. A create that succeeded without an id there calls `untrackedCreate` (`lib/data.js`): the response is logged as evidence, every identity-shaped value it carries (`id`, `_id`, `uuid`, `<type>Id`, at the top level or under `data`/`result`/`item`, or the `Location` header's last segment, never another field) is tracked, and with none an untracked marker goes to `results/<script>.untracked.json` and the summary line, for the triager to flag;
  - then the steps on the created entities, then the deletes, children first, each followed by `trackDeleted` after a 2xx;
- the cited think time as a commented `sleep()`, `teardown()` and `export { handleSummary } from '../lib/summary.js'`.

The k6-script-writer writes only the slot bodies of `scripts/slots/<m>.js` (`// k6-code:begin <key>` … `// k6-code:end <key>`): `data` (`setupData()`), `path:<EP>`, `query:<EP>`, `body:<EP>` and `checks:<EP>`. Slots hold data: no request, import, environment, `sleep`, `eval`, computed access, URL or secret-shaped literal. A random element of an array is `pick(array)` from `lib/data.js` (with `uniqueName` and `uniqueEmail`, the value slots' helpers). A rebuild keeps every body; a body whose slot is gone is parked in `k6/parked.json`. `build --adopt` moves an older hand-written `<m>-*.js` to `k6/legacy/`.

## Safety in code

- `lib/config.js` reads `BASE_URL` and `K6_ALLOWED_HOSTS` (comma-separated) from `__ENV` and **aborts in `setup()`** unless `BASE_URL`'s host is in the list. There is no default `BASE_URL`.
- A script whose workload scenario has `mutates: true` aborts unless `__ENV.ATF_MODE === 'full-run'`. k6 cannot call the ledger, so a flow records each entity it creates with `trackLeftover(type, ref)` from `lib/data.js` right after the create, and `trackDeleted(type, ref)` after a successful delete. `handleSummary` writes the entities created and not deleted to `results/<script>.created.json` (`[{type, ref}]`; k6 shares no state between VUs and `handleSummary`, so each record travels as a check name); the runner-triager records those in the ledger (`ledger.mjs add`) so they appear on the run's cleanup list.
- Live runs happen only in full-run runs (the guard enforces `load: run`); in readonly runs scripts are validated with `k6 inspect` only and results are recorded as `not-run`.

## Code rules

- `lib/summary.js` `handleSummary(data)` writes `results/<script>.summary.json` (the raw `data` object), `results/<script>.created.json` and a short text summary to stdout; the script name is `K6_SCRIPT` (else the options tag `script`).
- Checks via `lib/checks.js` helpers (status, JSON shape, latency); no `sleep()` without a think-time reason in a comment.
- Auth via `lib/auth.js` using env values only (`K6_USER`, `K6_PASSWORD`, or `K6_TOKEN`); never literals. There is no token exchange (no login request under load): `bearer`, `oauth2` and `api-key` send `K6_TOKEN`, `basic` sends `K6_USER` and `K6_PASSWORD`, `session` sends `K6_TOKEN` as the cookie the k6 overlay names (D-054).

**Machine-checked.** `workload.mjs check` (the designer's step): the schemas, both files equal to a fresh build, ids against the registry, one arrival-rate scenario per entry, `dropped_iterations`, nothing but smoke reads in readonly, a flow's cleanup, every catalogue endpoint accounted for. `k6-code.mjs check` (the script-writer's step): options and thresholds equal to `workload.json` (parsed, and through `k6 inspect` when k6 is on PATH), `dropped_iterations`, `assertAllowedHost()` and the right `requireFullRun(<mutates>)`, no write in a readonly workload, `trackLeftover`, the delete step and `trackDeleted` in a flow, no hard-coded URL or `BASE_URL`, commented `sleep()`, the endpoint tag on every request, `handleSummary`, one script per id (missing, duplicate, extra), no drift, and every slot rule. Each pass stamps its file `verified`, and the flow's step refuses a missing or stale stamp. The gate (`scripts/gate.mjs`, before every review) requires the workload's shape, `lib/config.js`, a current `k6-code.mjs check` stamp, no hard-coded URL in the scripts or the slot file, and (once rendered) no lib file drifted from its render. The reviewer judges the slot data, the extra checks and the workload's cited judgments.

## Running (k6-runner-triager only)

```
node <repo>/scripts/triage.mjs prepare <p> <m> --domain k6          # clears the module's stale summaries
ATF_MODE=full-run BASE_URL=<target> K6_ALLOWED_HOSTS=<target host> K6_SCRIPT=<m>-<scenario> k6 run scripts/<m>-<scenario>.js
node <repo>/scripts/results.mjs k6 <p> <m> k6-tests/<p>/results/<m>-*.summary.json
```
A failed smoke is re-run once with `K6_SCRIPT=<script>.retry` (summary `<script>.retry.summary.json`, which the `results.mjs` glob picks up): passing on the re-run is `flaky` by rule; no other script is re-run (D-058). The run is then triaged with `triage.mjs build` and `check` (`docs/agent-handoffs.md` §7): a failure against an `assumed` threshold is not a product bug by itself, and `results.mjs` maps results to workload scenarios by their `K6-` id.

Readonly run: `node <repo>/scripts/results.mjs not-run <p> <m> k6 --reason "readonly run: load tests only run in full-run"`.
