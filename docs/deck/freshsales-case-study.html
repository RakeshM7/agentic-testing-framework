Orchestrator

Drives all stages from one run-config file

Defined for both Claude Code and GitHub Copilot, reading and writing the same artifacts

The same seven personas exist in two flavors, one for Claude Code and one for Copilot. Both flavors use one shared artifact contract, so their outputs are interchangeable.

One config file drives six stages

#StageOutput
1ExploreSitemap, page snapshots, crawl log
2ClarificationFinal clarifications document
3Test casesCSV with a traceability index
4PlaywrightUI suite and created-entities log
5API testingAPI specs and test plan
6Feedback fixingOptional, off in this run

Halts and reports if a stage fails or a blocking question has no answer

The orchestrator reads a single run-config YAML. It halts instead of guessing when a blocking clarification question has no pre-written answer, which matters later in the case study.

One switch gates every mutation

readonly (default)

Non-mutating everywhere. Mutating tests are generated but skipped. No live load tests.

full-run

Set explicitly, per target, by a human authorized to test it. Mutating tests run live.

Even in full-run, deletes only touch records that run created itself, tracked in a created-entities log.

This is the hard safety rule in the repo. It is never inferred, and agents never self-grant it.

The case study

Freshsales: lead to deal

Create and qualify a lead, convert it to a contact and account, create a deal, move it across the Kanban pipeline, and log an activity along the way.

A multi-tenant SaaS CRM, tested on a personal 21-day trial tenant in full-run mode

There is no shared public Freshsales instance, so the run used a personal trial tenant. Full-run was only ever set against that tenant.

Five blockers before a single test ran

BlockerResolution
reCAPTCHA on the login pageLog in once by hand and save a session file
Session file not loadable at runtimePass it as a launch argument to the browser server
Stale browser holding the profile lockKill the leftover processes, restart the server
Answers not matching question wordingSwitch to short topic keywords
Wording drifting again on every runPair by topic, and file framework feedback

The agents never typed credentials or solved the CAPTCHA, by design

Each halt was the framework behaving as designed: stop and report instead of guessing, inventing credentials, or killing processes without approval.

A summary written by an agent is a claim. Re-running the suite is the check.

The 19 of 19 figure came from the orchestrator's report. When re-run, the first test in the lead-to-deal chain failed because the new contact did not appear in the list within 10 seconds, which left the other 11 tests in the chain unrun.

Where the skipped tests come from

CountWhereWhy
11UI suiteSerial chain: the first test failed, so the rest never ran
8Freshsales APIMutating tests need AUTHORIZATIONS_MODE=full-run in the environment
1Freshsales APIDeliberate placeholder: Leads 403 test is out of scope
6Old EventHub APILeftover tests from an earlier target, missing credentials or data

Three different causes: a failure, a safety guard, and stale tests

The word skipped hides three different things. A did-not-run after a failed serial test is a real problem. A guard skip is the safety rule working. The EventHub tests are noise from a previous target.

What the case study taught us

Match by topic

Pre-written answers must survive reworded questions. Exact-substring matching does not.

One source of truth

The config said full-run, but the guard read an environment variable. They disagreed.

Clean up on failure

A failed first test skips the cleanup tests, and live records stay behind.

Each lesson was filed as feedback for the implementor agent

All three came out of the run itself, and the agents filed feedback files for them under the feedback folder.

Next steps

  1. Fix the first lead-to-deal test so the chain can run end to end

  3. Run the 8 mutating API tests with full-run set in the environment
  4. Retire the old EventHub API tests

Deleting records and running mutating tests both need an explicit go-ahead

The first two items are the most urgent. The cleanup deletes only records the test runs themselves created.
